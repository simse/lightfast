# macOS release

Xcode packages the app: `macos/Lightfast.xcodeproj` wraps the `lightfast` cargo binary in
`Lightfast.app`, then signs and archives it. CI turns the export into a Developer ID signed,
notarized and stapled `Lightfast.dmg`.

## Layout

- `lightfast.xcodeproj`: generated by [cargo-xcode](https://crates.io/crates/cargo-xcode). Its one
  target runs `cargo build` for the `lightfast` binary, with the Debug and Release configurations
  mapped to cargo's `dev` and `release` profiles. It sits next to `Cargo.toml`, because the
  generated build rule resolves `Cargo.lock` and `src` from the project's directory. It doesn't
  need cargo-xcode to build. Regenerate it after adding, removing or renaming a binary:
  ```sh
  cargo install cargo-xcode --version 1.11.2 --locked
  cargo xcode --skip-install --platforms macosx --xcconfig macos/Lightfast.xcconfig
  ```
- `macos/Lightfast.xcodeproj`: the app. It has no sources of its own. It copies the binary into
  `Contents/MacOS`, compiles `assets/Lightfast.icon` and embeds Sparkle, a Swift package pinned to
  an exact version.
- `macos/Lightfast.xcconfig`: settings both projects share: macOS 27, Apple Silicon only. Xcode
  exports them to cargo, and rustc reads `MACOSX_DEPLOYMENT_TARGET`.
- `macos/Info.plist`: the keys that have no `INFOPLIST_KEY_` build setting. Xcode generates the
  rest from the target's build settings.
- `macos/ExportOptions.plist`: options for the Developer ID export.

The scanner drivers are the pure-Rust crates in `crates/` (`scan-pixma` over `nusb`, which
talks to IOKit directly), so there are no backend plugins or config files to bundle, and users
need nothing installed.

## Building locally

`cargo build` and `cargo run` need nothing beyond Rust (`rust-toolchain.toml` pins the
version), but only the bundled app has an icon and Sparkle.

Open `macos/Lightfast.xcodeproj` and run the Lightfast scheme. Debug builds are signed ad hoc,
so they need no certificate.

For a release build, use Product → Archive, then Distribute App → Direct Distribution, which
signs with Developer ID and notarizes. This needs the *Developer ID Application* certificate:
in Xcode, Settings → Accounts → (your team) → Manage Certificates → **+** → *Developer ID
Application*. That needs the Account Holder role. Check it with
`security find-identity -v -p codesigning`.

The command-line equivalent of an archive and export is the `archive` and `export app` steps in
`.github/workflows/build.yml`.

## Publishing a release

Tag a commit on `main` and push the tag:

```sh
git tag v0.1.0
git push origin v0.1.0
```

CI builds the DMG with that version, then publishes a GitHub release with
`Lightfast-0.1.0.dmg` and `appcast.xml` attached. Installed apps read the appcast from the
latest release, so publishing is what offers them the update. Only plain `vX.Y.Z` tags
release.

The tag is the source of truth for the version: CI writes it into `Cargo.toml` and passes it to
Xcode as `MARKETING_VERSION`. Untagged builds use the version committed in `Cargo.toml`.

## Updates

Sparkle fetches its feed from `SUFeedURL` in `macos/Info.plist`, and only accepts updates signed
by the private key matching `SUPublicEDKey`.

**Back up the private key.** It lives in the login Keychain of the Mac that created it, under
the Sparkle account `lightfast`, and in the `SPARKLE_ED_PRIVATE_KEY` secret, which can't be read
back. If it is lost, installed apps can't accept any further update. To export it, using
`generate_keys` from the resolved Sparkle package (`SourcePackages/artifacts/sparkle/Sparkle/bin`
in Xcode's DerivedData):

```sh
generate_keys --account lightfast -x lightfast-sparkle.key   # store it somewhere safe, then delete it
```

**Versions.** Sparkle compares `CFBundleVersion`, not the marketing version, to decide what is
newer. CI sets it (`CURRENT_PROJECT_VERSION`) to the build's UTC timestamp, `YYYYMMDD.HHMMSS`, the
format cargo-bundle used for earlier releases. `generate_appcast` copies it from the built app,
so the build most recently tagged wins, whatever its version number says. Keep the format: a
smaller number would stop installed apps from updating.

**Feed URL.** The URL depends on this repository's name and on it being public, since Sparkle
can't authenticate to GitHub. Renaming the repository leaves installed apps relying on GitHub's
redirect.

## CI

`.github/workflows/build.yml` builds a signed, notarized and stapled DMG on every push to
`main`, every pull request and every version tag, and uploads it as a workflow artifact. Version
tags also publish the release. `.github/workflows/checks.yml` runs rustfmt, clippy and the tests.

The build needs these repository secrets:

- `LIGHTFAST_P12_BASE64`: the Developer ID certificate and key. In Keychain Access → My
  Certificates, right-click *Developer ID Application: …* → Export, save it as `.p12` with a
  password, then `base64 -i developer-id.p12 | tr -d '\n' | gh secret set LIGHTFAST_P12_BASE64`
- `LIGHTFAST_P12_PASSWORD`: the password of the `.p12`
- `LIGHTFAST_NOTARY_KEY_BASE64`: an App Store Connect API key, `base64 -i AuthKey_XXXXXXXXXX.p8 | tr -d '\n' | gh secret set LIGHTFAST_NOTARY_KEY_BASE64`
- `LIGHTFAST_NOTARY_KEY_ID`: that key's ID
- `LIGHTFAST_NOTARY_ISSUER_ID`: the issuer ID shown above the list of keys
- `SPARKLE_ED_PRIVATE_KEY`: the exported Sparkle key, `gh secret set SPARKLE_ED_PRIVATE_KEY < lightfast-sparkle.key`

## Other platforms

Packaging is per platform, around one cargo binary that has no packaging metadata. Windows and
Linux would each get a `windows/` or `linux/` directory and a job in `build.yml` that runs
`cargo build --release` and packages the binary with that platform's tools, for example an MSI
or MSIX, and an AppImage or Flatpak. Sparkle and the glass UI are already `cfg(target_os =
"macos")`. Once GPUI builds on those platforms, the clippy and test jobs in `checks.yml` can
take an `os` matrix.

## Notes

- The app icon is `assets/Lightfast.icon`, a layered Icon Composer bundle. Edit it in Icon
  Composer. Xcode compiles it into `Contents/Resources/Assets.car`, plus a `Lightfast.icns`
  fallback, and sets `CFBundleIconName`, so macOS renders the dark, clear and tinted variants.
- The app isn't sandboxed and needs no entitlements beyond the hardened runtime, so it has no
  entitlements file.
